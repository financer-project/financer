Contracts the executor needs without re-deriving them:

- `FilterStrategy<T, C>` (`src/lib/components/common/data/table/filters/types.ts`) — two members: `Component: React.FC<{ config: C; currentValue: string | null; onChange: (val: string | null) => void }>` and `getWhereClause: (config: C, value: string) => Record<string, unknown>`. Any fix must stay inside this interface (CONTEXT.md "Established Patterns").
- `SelectFilterConfig<T>` — `{ type: "select"; property: keyof T | string; label: string; options: { label: string; value: string; render?: (label: string) => ReactNode }[]; multiSelect?: boolean }`.
- `buildPrismaWhere` (`prisma-filter-builder.ts`) returns `{ AND: [...] }` when any clause is active, `{}` otherwise. It reads each filter's value from the URL by `filter.property` and skips falsy values.
- `getTransactions` resolver merges as `where = { ...where, account: { householdId } }` — top-level Prisma fields are ANDed, so household isolation survives an incoming `AND`/`OR` clause.
- Prisma schema facts verified this session: `Transaction.counterpartyId` is `String?` (a real nullable scalar, so `{ counterpartyId: { in: [...] } }` is a structurally valid `TransactionWhereInput`). `Transaction` has **no** `tagId` scalar — tags are the `TransactonTags[]` relation named `TransactionTags`.
- Existing Cypress helpers (declared in `test/cypress/support/e2e.ts`, implemented in `test/cypress/support/commands.ts`): `cy.selectField({ contains | for | label, value | values })`, `cy.findSelectField({...})`, `cy.resetAndSeedDatabase(cb)`, `cy.loginWithUser(user)`.
